# 近即時正射處理：模擬器（第一階段：假航照產生器）

目的：無人機採購規範（簡報版）要求「每月處理 2,000 張原始影像、GSD 5 cm、OGC WMTS、航跡即時同步」。
真實相機與原始航照尚未取得，所以先用已知地面真值合成，驗證「上傳 → 增量鑲嵌 → 圖磚更新」管線與延遲。

## 為什麼用合成資料
- 台灣有帶 RTK 的原始航拍（ODM 社群的 `tuniu_tw_1`/`tuniu_tw_2`，苗栗頭份，Phantom 4 RTK），但都是 2 GB 級整包壓縮檔、**頁面未標示授權**，
  GPS／姿態欄位**尚未驗證**，所以沒有下載。要用時請先向上傳者確認授權。
- OpenAerialMap 的台灣成果多是已拼接的 GeoTIFF，沒有逐張 EXIF／姿態，只適合當地面真值。

## 產生器：`scripts/sim/sim_aerial_gen.py`
地面真值＝NLSC `PHOTO3826`（EPSG:3826 第 13 層，0.265 m/像素），依割草機式航線（前後重疊 80%、左右重疊 70%）切出 1024×768 假影像，
寫入 EXIF（GPS 經緯度、海拔、拍攝時間、航向）與 DJI 風格 XMP（`GimbalYaw/Pitch/RollDegree`、`FlightYaw/…`、`RelativeAltitude`、`RtkFlag`；
欄位名稱仿 DJI，值是合成的），另輸出 `manifest.json`（每張的**真實姿態**與**紀錄姿態**）。
真實姿態含風造成的俯仰／橫滾偏差（σ≈1°）與航向抖動（σ≈1.5°）；紀錄姿態為 RTK 定位雜訊 σ≈2 cm（`--no-rtk` 為 σ≈1.5 m）加姿態感測器雜訊 σ≈0.1°。

```
python scripts/sim/sim_aerial_gen.py --out <版本庫外的資料夾> --size 700x450
python scripts/sim/sim_aerial_verify.py <同一資料夾>
```

## 驗證結果（700×450 m、100 m AGL、RTK、seed 1）
| 項目 | 結果 |
|---|---|
| 張數、航線 | 108 張、6 條航線；拍攝間距 40.6 m、航線間距 81.3 m；任務約 8.1 分鐘（10 m/s） |
| EXIF 位置讀回誤差 | 最大 0.0019 m（度分秒量化） |
| 姿態（XMP）讀回誤差 | 最大 0.005° |
| 直接地理定位誤差（footprint 中心） | 平均 0.24 m、P95 0.42 m、最大 0.51 m |

## 限制（務必理解）
- **GSD 是 0.265 m，不是規範的 5 cm**：受限於地面真值解析度。規範的 5 cm 對應 EPSG:3857 的 z21（約 6.9 cm/像素）；z22 是放大，規範明載「無假性插值放大」，最大縮放建議限制在 z21。
- 平坦地面、針孔相機、無鏡頭畸變、無地形起伏，姿態只用位移近似；**不能驗證真實相機的空三精度**。直接地理定位的誤差是理想值。
- NLSC 影像帶「nlsc.gov.tw 2021」浮水印，授權條款尚未確認：**只存本機，不進版本庫、不上 HF**。`--out` 請指向版本庫外。

## 第二階段：上傳端點與增量鑲嵌（cargo feature `ingest`）
`cargo build --release --features ingest`（預設不編入，HF 映像不受影響）。設定見 `config/layers.local.toml` 的 `[ingest]` 與 `orthophoto_live` 圖層。

| 端點 | 說明 |
|---|---|
| `POST /api/v1/ingest/frame?session_id=…` | body＝原始 JPEG。讀 EXIF GPS／海拔與 XMP 姿態 → 投影到 EPSG:3857 z19 與 EPSG:3826 第 13 層 → 只重寫受影響圖磚。以 SHA-256 冪等；全部經 `require_auth` |
| `GET /api/v1/ingest/stats` | 張數、圖磚數、處理時間 p50/p95/max、重複／拒絕／失敗次數 |
| `GET /api/v1/ingest/audit?limit=` | 稽核紀錄（身分、來源 IP、結果），最新在前 |

實作要點：自己實作的 TM2 與經緯度互轉（Krüger 級數）對 pyproj 的誤差 < 1 mm（單元測試）；單一鎖序列化鑲嵌，避免兩張影像同時改同一塊圖磚；
圖磚用「寫暫存檔再改名」更新，讀取端不會讀到半張；`orthophoto_live` 的 `Cache-Control: max-age=2`（`LayerConfig.cache_seconds`，其他圖層維持 86400）。

### 金字塔與內建檢視器（第二階段後半）
- **金字塔**：`[ingest].targets` 每個目標可設 `pyramid = N`，每次鑲嵌後由「下一級較細的圖磚」重算受影響的 N 個較粗級別（`build_pyramid`）。
  用 k×k 取樣的箱形濾波（k = ceil(解析度比)），不假設 2 倍比例，所以 TWD97 的 2.5 倍層級也適用；只計入有資料的取樣點，全無資料保持透明。
  目前設定 z19→z15（Web Mercator）與第 13→9 層（TWD97）。單元測試涵蓋 2 倍與 2.5 倍兩種比例。
- **內建檢視器**：「連線設定」面板新增「切到近即時圖層」按鈕（設 Layer＝`orthophoto_live`、TMS＝GoogleMapsCompatible、開啟近即時更新，並依 GetCapabilities 的範圍移到該圖層）；
  「圖層」面板新增「近即時更新（每 3 秒）」核取方塊：每 3 秒逐塊重取目前畫面的圖磚，先離屏預載再換圖，不閃爍；分頁隱藏時暫停。
- **瀏覽器驗證**（`scripts/sim/smoke_live_viewer.py`，無頭 Edge，8/8）：按鈕切換正確、地圖移到範圍中心；重播期間 z17 視窗內已載入圖磚從 0 逐步增加到 13；
  縮放 15（金字塔）與 19（原生）都有圖；無 JS 例外。既有的 `smoke_mapsearch.py`（43/43）、`smoke_pikmin.py`（21/21）、Rust 測試（含 ingest 共 10 項）都通過。

### 曾遇到的環境問題（已排除）：伺服器程序處理影像時被外部終止
2026-10-10 在開發機上，HTTP 上傳的伺服器程序曾在寫入第三塊圖磚時被終止（結束代碼 0、無任何錯誤輸出），連稍早通過的已提交版本也一樣，
所以不是程式碼退化。已排除程式內部呼叫結束（以偵錯器在 `ExitProcess`／`TerminateProcess`／`NtTerminateProcess` 設中斷點，沒有命中）、崩潰、
輸出位置與執行檔路徑；同樣的處理流程在測試程序裡完全正常。當時機器上有 Windows Defender 與趨勢科技 PC-cillin，記錄裡沒有直接證據；
把防毒軟體排除後，**含金字塔的完整 HTTP 端到端測試通過**（見下表），因此推測是防毒軟體的即時防護，但終止者本身未能從記錄確認。
若在你的環境遇到類似現象，把 `target\` 與 `tiles\orthophoto_live` 加入防毒排除清單。
測試輔助 `stream_frames_to_tiles`（`cargo test --release --features ingest stream_frames_to_tiles -- --ignored --nocapture`，環境變數 `FRAMES_DIR`、`TILE_DIR`、
`INTERVAL_MS`、`LIMIT`）保留：它與 ingest 端點用同一組鑲嵌與金字塔程式，可在不啟動伺服器程序的情況下產生持續變動的圖磚，
`smoke_live_viewer.py --mode cargo` 就是用它。

### 效能優化與重測（含金字塔、HTTP 路徑，108 張，同一臺機器）
加入金字塔後單張處理曾從約 170 ms 退到約 2.1 s（p50）。量測顯示大宗是 PNG 編碼與檔案寫入（每張約 65 塊，每塊 7–12 ms）加上逐像素的雜湊表查詢。處理：
金字塔每個父圖磚先算好取樣座標表、像素迴圈只做陣列索引；PNG 改快速壓縮（`CompressionType::Fast`＋`FilterType::Sub`）；圖磚之間互不相干，
鑲嵌與金字塔改以多執行緒處理（`std::thread::scope`，上限 8 條）。

|---|---|---|
| 伺服器處理時間 p50／p95／max | 2133／3213／4573 ms | **279／713／752 ms** |
| 上傳→圖磚可讀 p50／p95 | 2194／3254 ms | **402／781 ms** |

### 稽核（401／403／429）
`src/audit.rs`。驗證失敗、來源網域被拒、限流都寫入 `audit_log`（影像上傳結果原本就有）：

| 結果（outcome） | 觸發 | 原因代碼 |
|---|---|---|
| `unauthorized` | 401 | `no_credentials`、`unknown_api_key`、`invalid_bearer` |
| `forbidden` | 403 | `origin_or_referer`（detail 含被拒的 Origin／Referer） |
| `rate_limited` | 429 | `api_key_rate_limit`（actor＝`apikey:<label>`） |
| `ok`／`duplicate`／`rejected`／`failed` | 影像上傳 | — |

設計取捨：成功的驗證不記（每張圖磚都記會灌爆資料庫，也沒有稽核價值）；**密鑰值永遠不寫入**；同一個（來源 IP, 結果:原因代碼）在 10 秒視窗內只寫一筆，
被略過的次數併入下一筆的 `suppressed=N`，所以攻擊者灌壞請求不會撐爆稽核表、也不會漏算次數；節流 key 用固定的原因代碼而不是 detail，避免攻擊者換字串繞過。
`X-Forwarded-For` 只在 `behind_reverse_proxy = true` 時信任（先前 ingest 無條件信任，已修正）。查詢：`GET /api/v1/audit?outcome=…&action=…&limit=…`
（`/api/v1/ingest/audit` 仍保留作別名）。

#### 防竄改、驗證、匯出、保存期限
- **雜湊鏈**：每筆存 `prev_hash` 與 `hash = SHA-256(prev_hash ‖ 各欄位)`，欄位以 4 位元組長度前綴編碼（避免欄位邊界被移動的歧義，有單元測試）。
  修改任何一筆、刪除中間任何一筆、調換順序，`GET /api/v1/audit/verify` 都會在該處斷鏈並回報 `first_bad_id` 與原因。用另開的唯讀連線驗證，不佔寫入鎖。
- **限制（務必知道）**：能直接寫資料庫檔案的人可以**重算整條鏈而不被發現**（端到端測試實際做了這件事：重算後單看資料庫驗證仍通過）。
  所以要把「鏈頭」（驗證回應與匯出清單都有 `head_id`、`head_hash`）**定期存到資料庫之外**（另一台機器、唯讀儲存、簽章後寄出），
  驗證時帶 `expected_id`＋`expected_hash`：重算過的鏈在該筆的雜湊不同，`anchor_match=false`（測試實際抓到）。
- **匯出**：`GET /api/v1/audit/export?from=&to=&outcome=` → JSON Lines，每筆一行（含 `prev_hash`、`hash`），最後一行是 `{"manifest": …}`（筆數、首末 id、鏈頭、鏈是否完整、匯出時間）。
  匯出檔可以**不信任伺服器、用獨立程式重算雜湊鏈**驗證（測試用 Python 重算全部吻合）。匯出動作本身也寫一筆稽核（誰、範圍、當時鏈是否完整）。上限 20 萬筆。
- **保存期限**：`[audit] retention_days`（預設 0＝**不自動清除**；稽核資料不宜默默消失）。啟用時每 6 小時清除一次，清除前把被清除的最後一筆的雜湊記進 `audit_anchor`，
  清除後鏈仍可驗證；清除動作本身寫一筆 `audit_prune` 稽核。**清除不可逆，請先匯出**。
- **舊資料庫相容**：啟動時自動補欄位；沒有雜湊的舊紀錄列為 `unchained_rows`，不算驗證失敗，也不在鏈上（它們無法被保證未被竄改）。
- **驗證**：雜湊鏈單元測試 7 項（雜湊編碼無歧義、完整鏈、修改、刪除中間、重算鏈只有外部錨點抓得到、清除後經錨點仍可驗證且清除後再刪會斷鏈、舊版資料庫）；
  端到端 `scripts/sim/test_audit_chain.py` 11 項全過（含直接改資料庫檔案的竄改偵測）；保存期限另以種入舊版資料庫實測：過期的舊紀錄被清除、近期的保留、清除動作被稽核、驗證通過。
- **存取控制（角色分權）**：稽核（`/api/v1/audit`、`/verify`、`/export`、`/api/v1/ingest/audit`）與可用率報表限 `admin`；上傳影像與處理統計限 `uploader` 以上；其餘讀取是 `client`（預設、最小權限）。
  API Key 在設定檔以 `role` 指定、JWT 以 `role` 聲明（沒有或未知值當 `client`，不升權）。權限不足回 403 並寫入稽核。端到端 `scripts/sim/test_roles.py` 驗證 9 個端點 × 4 種身分（未驗證／client／uploader／admin）的狀態碼矩陣、
  JWT 的 admin／uploader／無 role／未知 role／簽章被竄改，以及拒絕被稽核且不含任何金鑰。
- **仍缺**：把鏈頭自動送到外部（目前要操作員自己定期取用）；匯出檔的簽章。

### 健康檢查與可用率報表（對應規範「API 可用率 ≥ 99.5%（月）」）
`src/health.rs`。

- `GET /healthz`：存活（既有）。`GET /readyz`（免驗證）：實際寫一筆資料庫、檢查圖磚來源，失敗回 503；回應只有布林與計數，不含路徑。
- `GET /api/v1/availability?month=YYYY-MM&tz=8`（需驗證；亦可用 `from`／`to` 指定自訂期間，並以 `detail=true` 取得逐分鐘狀態）：月可用率報表，含可用／停機分鐘、可用率、是否達標、容許停機分鐘與剩餘額度、停機事件清單（起點、分鐘數、種類）。
- **定義**：背景工作每 10 秒自我探測（資料庫可寫、至少一個圖磚來源可讀），每分鐘寫一筆 `uptime_samples`（探測次數、失敗次數、請求數、5xx 數）。
  一分鐘「可用」＝有紀錄、探測全成功、5xx 比例 ≤ 5%（沒有請求不看比例）。**沒有紀錄的分鐘算不可用**（行程沒在跑就寫不出紀錄）。分母從該期間第一筆紀錄算起，部署前的時間不扣。
  事件種類：`no_data`（沒紀錄＝停機）、`unhealthy`（有紀錄但探測失敗或 5xx 過高）、`mixed`。
- **驗證**：單元測試 7 項（全可用、停機事件、探測失敗與 5xx 邊界、混合事件、起算點與當前分鐘排除、99.5% 恰好達標、月份與時區換算）；
  端到端 `scripts/sim/test_health_audit.py` 全數通過（含 60 次壞請求只多寫 ≤ 2 筆稽核、限流 429 與稽核、密鑰不外洩、可用率報表）；
  並實際把伺服器關掉再重啟：被關掉的那一分鐘被偵測為 1 個 `no_data` 事件，可用率 66.7%，`meets_target=false`。
- **盲點（務必知道）**：這是服務「自己量」的可用率。機器關機、網路斷線、反向代理或 DNS 故障時，它只會呈現成「沒有紀錄的分鐘」（方向對，但分不出原因，也量不到代理層的問題）。
  行程當掉的**那一分鐘**內部仍算可用（行程無法預先回報自己即將停止）；重啟的那一分鐘，若行程是在該分鐘第 10 秒之後才起來，會記為不健康（全新部署不套用）。
  **正式驗收要另外用外部探測交叉比對**，見下節。

### 外部探測與交叉比對（`scripts/probe_readyz.py`）
- `probe`：從伺服器外面每隔 N 秒（預設 10）對 `/readyz` 取樣，附加寫入 JSON Lines；放在另一台機器長期執行。
- `compare`：以記錄涵蓋的完整分鐘為期間，向伺服器取逐分鐘狀態（`GET /api/v1/availability?from=…&to=…&detail=true&strict=true`，期間 ≤ 2 天；`strict` 表示嚴格從 `from` 起算、沒有紀錄的分鐘算停機），
  逐分鐘比對並列出不一致：「外部停機但內部可用」（內部盲點）與「外部可用但內部停機」（內部誤報）；不一致超過 `--tolerance` 時結束代碼為 1。
- **實測**（探測間隔 5 秒；14:00 啟動、14:02:15 關掉伺服器、14:03:55 重啟）：判定 4 分鐘，一致 3、不一致 1；不一致的是行程被關掉的那一分鐘（14:02）——
  外部看到停機，內部因為行程在該分鐘中途結束、之前的探測都成功而算可用，即上述原理上的盲點；停機期間與重啟那一分鐘（14:03）兩邊一致為停機。
  第一次比對時還有「外部可用但內部停機」的誤報（行程被關掉那一分鐘沒有留下紀錄），已改為每次探測都累加寫入當分鐘的紀錄後消除。
  結論：每次非預期的行程中止，內部報表最多少算約 1 分鐘；用外部探測的數字當驗收依據。

### 機隊同時回傳模擬（22 架）：改善前與改善後
工具：`scripts/sim/sim_fleet_gen.py`（為每架機產生各自的任務影像：22 個互不重疊的 1 km 間隔任務區，各 450×300 m，共 1,056 張）、
`scripts/sim/sim_fleet.py`（並行上傳模擬＋報表，`--spawn` 每次用全新伺服器）、`scripts/sim/sim_fleet_shots.py`（同時用無頭 Edge 開檢視器截圖，`--headed` 可開視窗即時看）、
`scripts/sim/make_fleet_gif.py`（把兩次截圖組成前後對比動畫，影像授權未確認，只存本機）。
**客戶端模型是我的假設**：每架機依任務的真實拍攝節奏（約每 4 秒 1 張）拍攝，影像先進先出、**一次只上傳一張**，上傳不及就在機上排隊（存儲轉發）；
收到 503（伺服器忙）或 409（這張正在處理）就依 `Retry-After`（2 秒）退避後重送，不丟影像；逾時則最多重試 3 次。
指標「拍攝→圖磚可見」＝上傳完成時刻 − 拍攝時刻，包含機上排隊、網路、伺服器排隊與處理。真實的機上上傳程式行為未知，數字隨之改變。
測試在 32 核心的開發機上，伺服器與客戶端同一臺機器（沒有真實網路延遲與頻寬限制），檔案寫入延遲波動大，數字僅供相對比較。

**改善前（單一全域鎖，整個處理一張一張依序做）** — 22 架、真實節奏：到達 4.8 張/s，伺服器只能處理 2.65 張/s；拍攝→可見 p50 **79 s**、p95 **163 s**、最大 177 s，
延遲從 3 s 一路線性上升到 86 s（沒有穩態）；任務結束後又花 180 s 才排空（399 s 完成 220 s 的任務量）。能持續撐住約 12 架，16 架就失控（見下方舊掃描）。

**改善後（圖磚級鎖＋並行處理＋入場控制）** — 同樣的 22 架、真實節奏（並行度 4）：

| 項目 | 改善前 | 改善後 |
|---|---|---|
| 伺服器吞吐 | 2.65 張/s | **4.56 張/s**（≈ 到達速率 4.70） |
| 拍攝→可見 p50／p95／最大 | 79／163／177 s | **4.4／7.5／10.2 s**，有穩態，沒有累積 |
| 任務結束後排空 | 180 s | **12 s** |
| 完成 1,056 張的總時間 | 399 s | **231 s**（任務本身 220 s） |
| 伺服器端排隊 p50 | 7.7 s | 3.0 s |
| 公平性（各機平均延遲） | 76–84 s | 3.5–4.9 s，每架都完成 48 張 |
| 壓力下 GetTile／`/readyz` p95 | 31／107 ms | 30／132 ms（0 失敗） |

單張處理時間在並行下變長（p50 262 → 720 ms，因為四張同時搶 CPU 與磁碟），但整體吞吐更高，等待時間大幅下降。

**吞吐量隨並行度**（22 架、拍攝節奏 ×3＝到達 13.6 張/s 的過載，量最大吞吐）：2 路 3.57、4 路 4.66、**8 路 5.49**、16 路 5.20 張/s。8 路之後 CPU 與磁碟成為瓶頸、不再增加。
預設並行度因此依核心數決定：`concurrency = max(2, 核心數 ÷ 4)`（32 核心＝8），可在 `[ingest]` 覆寫。
節奏 ×2（到達 9.2 張/s）時 4 路又飽和（吞吐 4.16、拍攝→可見 p50 49 s），所以**現在的上限大約是 22–25 架連續回傳**（8 路約 5.5 張/s ÷ 0.22 張/s/架），不是無限。

**入場控制**（`[ingest] max_queue`，預設 64）：等待處理名額的影像超過上限就回 **503＋`Retry-After: 2`**，並寫入稽核（`busy:queue_full`，節流）。
實測（並行度 4、佇列上限 8、22 架）：276 次 503，客戶端退避後重送，客戶端退避後重送、不丟影像（報表另列的「失敗 9」是測試結束時仍在重試的上傳被計為失敗；這是依程式邏輯的推斷，沒有逐一核對）；
拍攝→可見 p50 3.3 s、p95 12.7 s、最大 29.9 s，吞吐 4.29 張/s，讀取端不受影響。觀察到的缺點：客戶端固定 2 秒、沒有抖動的退避會同步重試，各機完成張數不均（14–20）；**真實的機上程式應該加隨機抖動**。
同一張影像（相同 SHA-256）正在處理時再收到 → **409**（不重複處理）；處理完成後再送 → `duplicate`。

**逾時較短時（改善前的實測，客戶端逾時 6 s、最多重試 3 次）**：80 次逾時、80 次重試、6 張在客戶端被放棄；伺服器處理了 258 張，比客戶端確認成功的 250 張多 8 張
（處理完成但客戶端已逾時放棄的影像）。改善後排隊時間縮短、且有 503 退避，這個情境沒有重測。

**並行的正確性**：
- 不同影像同時改同一塊圖磚會互相覆蓋，所以加了**圖磚級鎖**（鑲嵌的「讀舊→混合→寫回」與金字塔的「讀子圖磚→重算→寫回」都在該圖磚的鎖內；每個執行緒同時只持有一把鎖，不會死結）。
- 金字塔父圖磚**在鎖內才讀子圖磚、不跨父圖磚快取**：最後一個重算該父圖磚的影像，讀到的一定是所有影像寫完子圖磚之後的內容（每張影像是在自己寫完子圖磚後才重算父圖磚）。
- 單元測試 `concurrent_frames_keep_pyramid_consistent`：6 張互相重疊的影像同時鑲嵌＋金字塔後，所有金字塔層級的圖磚必須與「由最終子圖磚重新計算」逐像素相同（Web Mercator 與 TWD97 各一次）。
  **突變驗證**：把金字塔父圖磚的鎖拿掉，這個測試就失敗（並行寫同一暫存檔），所以測試有鑑別力；但它抓的是「缺鎖」，不保證抓得到所有可能的競爭順序。

**仍然存在的限制**
- 這是 22 架**全部連續回傳**的壓力情境；若實際負載是規範的每月 2,000 張，完全不是問題。
- 解析度 0.265 m；5 cm 的 16 MP 影像每張工作量是數倍，**撐得住的機數會更少，尚未量測**。
- 金字塔每張影像仍會重算受影響的上層圖磚（沒有合併／延後）；粗級別的圖磚被很多機共用，是主要的鎖競爭點。
- 處理完成但回應遺失的影像，重送時伺服器會再處理一次（先記「處理中」的方案尚未做）。
- 沒有真實網路延遲、頻寬限制與客戶端抖動；機隊影像是同一張底圖切出來的合成資料。

### 限制與未做
- GSD 仍是 0.265 m（地面真值限制）。規範的 5 cm 情境（16 MP、z21）每張約涵蓋 250 塊圖磚、解碼 16 MP，單張處理時間**預期是這次的數倍，尚未量測**。
- 沒有真實鑲嵌線選擇／色彩平衡，混合只做邊緣羽化。金字塔每張影像都重算受影響的上層圖磚，張數多時成本會增加（沒有合併或延後更新）。
- 鑲嵌是「讀舊圖磚→混合→寫回」，以圖磚級鎖保護；多張影像可並行處理，單張影像內的圖磚也以多執行緒處理。多客戶端並行處理（圖磚級鎖，預設並行度＝核心數 ÷ 4），22 架連續回傳可穩態處理（見「機隊同時回傳模擬」），上限約 22–25 架。
- 一般客戶端上傳大檔時若驗證失敗，伺服器在讀完 body 前就回 401 並關線，Windows 客戶端可能看到連線重置而非 401（測試以小 body 驗證 401）。
- 稽核：鏈頭沒有自動送出到外部、匯出檔沒有簽章；可用率需外部探測交叉驗證（見上）。
- 姿態慣例是模擬慣例（見 `src/ingest/mosaic.rs` 檔頭）；接真實 DJI 資料時要核對偏航與雲台角度的符號。
